# Frontend Comparison

This is generated by asking question on Web frontend to ChatGPT

Modern frontend frameworks such as React, Vue, Angular, Svelte, SolidJS, Qwik,
and Astro use different approaches to update the user interface, manage state,
and render web applications.

## 1. Reactivity and rendering

Signal-based reactivity is a programming model in which changes to individual
pieces of data automatically trigger updates to the specific parts of the UI
that depend on them.

A signal is essentially a reactive variable. For example:

```
const [count, setCount] = createSignal(0);

<button onClick={() => setCount(count() + 1)}>
  {count()}
</button>
```

When `count` changes:

- The framework knows which UI elements depend on `count`.
- Only those dependent elements need updating.
- The entire component does not necessarily need to execute again.

Why it matters: It enables fine-grained updates, potentially reducing
unnecessary rendering and improving performance.

### Re-render

A re-render occurs when a framework executes a component again to determine
whether its UI needs updating. Consider this React example:

```
function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <h1>Counter</h1>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </>
  );
}
```

When `count` changes, React executes the `App` component again.

Potential problems include:

1. Unnecessary work: Components may execute even when their displayed output
   hasn't changed.

2. Cascading renders: Updating a parent can cause child components to render
   again.

3. Performance overhead: Large component trees can require substantial
   reconciliation work.

4. Expensive calculations: Components may repeat calculations unnecessarily.

These problems can be addressed through component design, memoization, and
other optimization techniques. Importantly, a React re-render does not
necessarily mean that the browser updates the DOM. React can determine that the
actual DOM does not need changing.

### Hydration

Hydration is the process of attaching JavaScript functionality to HTML that was
already rendered on the server. For example:

1. The server generates HTML containing a product listing.
2. The browser receives and displays that HTML immediately.
3. JavaScript downloads.
4. React attaches event handlers and makes the page interactive.

A hydration bug occurs when the HTML generated by the server doesn't match what
the client-side framework expects during hydration. Example:

```
function App() {
  return <p>{Date.now()}</p>;
}
```

The server might generate:

```
<p>1793000000000</p>
```

But when the browser executes the component, it generates a different
timestamp. The mismatch can produce a hydration warning or force React to
regenerate part of the UI.

Other common causes:

- Different server and browser time zones.
- Random numbers generated during rendering.
- Browser-only APIs such as `window` or `localStorage`.
- Different data available on the server and client.
- Incorrect HTML nesting.

Why it matters: Hydration bugs can cause visual inconsistencies, additional
rendering work, and broken interactions.

### Suspense waterfalls

A Suspense waterfall occurs when asynchronous operations happen sequentially
even though they could potentially happen in parallel. Imagine a page that
needs three pieces of information:

- User profile: 500 ms.
- Orders: 500 ms.
- Recommendations: 500 ms.

Sequential loading total: 1,500 ms

Parallel loading total: 500 ms

Suspense waterfalls can happen when nested components suspend while waiting for
data, and the next operation cannot begin until the previous one finishes.
Avoiding waterfalls reduces page-loading time and improves perceived
performance.

## 2. Virtual DOM and optimization

The Virtual DOM is an in-memory representation of the browser's actual DOM
(Document Object Model). React uses it to determine what changes need to be
made to the real DOM.

Consider changing a counter from 1 to 2. React broadly performs these steps:

1. Executes the relevant component.
2. Creates a new Virtual DOM representation.
3. Compares it with the previous representation.
4. Identifies differences.
5. Updates the actual browser DOM where necessary.

Advantages

- Provides a declarative programming model.
- Developers describe what the UI should look like rather than manually
  manipulating DOM elements.
- Makes complex UI updates easier to manage.
- Reconciliation handles many DOM update details automatically.
- Supports a consistent component architecture.

Disadvantages

- Creating and comparing Virtual DOM trees consumes CPU and memory.
- Components can execute unnecessarily.
- Reconciliation introduces additional processing.
- Developers sometimes need memoization to avoid unnecessary work.

An important distinction: The Virtual DOM is not inherently slow. It provides a
convenient abstraction, and its performance depends on the framework's
implementation and application architecture. Frameworks such as SolidJS use
fine-grained reactivity instead of a traditional Virtual DOM reconciliation
approach.

### Manual memoization

Memoization means remembering the result of a calculation or function so that
it doesn't need to be recomputed unnecessarily. Manual memoization means
developers explicitly identify which calculations, components, or functions
should be cached. For example:

```
const expensiveResult = useMemo(() => {
  return calculateSomething(data);
}, [data]);
```

The result is reused as long as `data` hasn't changed.

Without memoization, the calculation might execute on every render. It can
improve performance, but it adds complexity. Developers must understand
dependencies and ensure that cached values remain valid.

Modern React also has React Compiler, which can automate many memoization
optimizations.

### Unit of reactivity

The unit of reactivity is the smallest piece of the application that the
framework tracks and updates when data changes. Different frameworks use
different units.

| Framework | Typical unit of reactivity                   |
| --------- | -------------------------------------------- |
| React     | Component                                    |
| SolidJS   | Signal / reactive computation                |
| Vue       | Reactive property / effect                   |
| Svelte 5  | Reactive state or derived expression (runes) |
| Angular   | Signal / view update mechanism               |

Suppose a page contains:

- A shopping cart.
- A customer profile.
- A product listing.

If the shopping cart quantity changes:

- In a component-based approach, the component containing the state may execute
  again.
- In a fine-grained reactive approach, only the UI elements dependent on the
  changed quantity may update.

Smaller units of reactivity can reduce unnecessary computation and improve
performance.

## 3. React hooks

These three concepts are particularly important in React.

### useEffect hooks

`useEffect` allows a React component to synchronize with external systems.
Common uses include:

- Fetching data.
- Setting up subscriptions.
- Registering event listeners.
- Starting timers.
- Interacting with external libraries.

Example:

```
function App() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    document.title = `Count: ${count}`;
  }, [count]);

  return <button onClick={() => setCount(count + 1)}>
    Increment
  </button>;
}
```

Whenever `count` changes, React runs the effect and updates the browser tab title.

The dependency array controls when the effect runs:

| Dependency          | Behavior                     |
| ------------------- | ---------------------------- |
| No dependency array | After every committed render |
| `[]`                | After initial mounting       |
| `[count]`           | When `count` changes         |

Effects can also return a cleanup function to remove subscriptions or event
listeners. Important: `useEffect` is not intended for every calculation or
state update. If something can be calculated directly from existing props or
state, an effect is usually unnecessary.

### useMemo calls

`useMemo` caches the result of a calculation between renders.

Example:

```
const filteredProducts = useMemo(() => {
  return products.filter(product =>
    product.price < maxPrice
  );
}, [products, maxPrice]);
```

The calculation is repeated only when `products` or `maxPrice` changes. Without
`useMemo`, React would perform the filtering calculation every time the
component renders.

### useCallback calls

`useCallback` caches a function definition between renders. Example:

```
const handleClick = useCallback(() => {
  setCount(count => count + 1);
}, []);
```

React normally creates a new function when a component executes again.
`useCallback` preserves the same function reference unless its dependencies
change.

Consider a parent component passing a function to a child component. If the
function is recreated on every render, the child may detect that its props have
changed and render again.

`useCallback` can prevent this when used with appropriate memoized children.

A useful way to remember:

- `useMemo`: Remember the result.
- `useCallback`: Remember the function.
- `useEffect`: Perform an external side effect.

## 4. Rendering architecture and server-side functionality

### Isomorphic framework

An isomorphic framework allows application code to execute in both server and
browser environments. For example, a React application using Next.js can:

1. Execute JavaScript on the server.
2. Generate HTML.
3. Send the HTML to the browser.
4. Hydrate the page.
5. Continue executing JavaScript in the browser.

This provides several benefits:

- Faster initial content display.
- Better search-engine indexing.
- Shared code between server and browser.
- Server-side access to databases and other resources.

Modern terminology often uses universal or server/client rendering rather than
isomorphic, because not all code necessarily runs in both environments.

### Islands Architecture

Islands Architecture is a web development approach in which most of a page is
rendered as static HTML, while only selected interactive components are
hydrated with JavaScript.

Imagine an e-commerce page:

- Product description: Static HTML.
- Product images: Static HTML.
- Navigation: Interactive island.
- Shopping cart: Interactive island.
- Customer reviews: Potentially static HTML.

Instead of making the entire page interactive through JavaScript, only the
components requiring interaction receive JavaScript. The concept is
particularly associated with Astro.

Advantages:

- Less JavaScript downloaded.
- Faster initial page loading.
- Reduced hydration work.
- Better performance on slower devices.

### Lighthouse score

Lighthouse is Google's open-source tool for measuring website quality. It
evaluates websites across four categories:

| Category       | What it measures                              |
| -------------- | --------------------------------------------- |
| Performance    | Loading speed and responsiveness              |
| Accessibility  | How accessible the website is                 |
| Best Practices | Security and modern web development practices |
| SEO            | Search engine optimization                    |

Each category receives a score from 0 to 100.

Typical score interpretation:

| Score  | Assessment        |
| ------ | ----------------- |
| 90–100 | Good              |
| 50–89  | Needs improvement |
| 0–49   | Poor              |

Lighthouse helps developers identify performance and usability problems. A
Lighthouse score is a laboratory measurement, however, and doesn't necessarily
represent the experience of every real-world user.

### Out-of-Order streaming

Out-of-Order streaming is a rendering technique that allows a server to send
parts of a web page as soon as they are ready, without waiting for every part
of the page to finish rendering.

Imagine a page with:

- Header: Ready immediately.
- Product information: Ready after 100 ms.
- Recommendations: Ready after 1,000 ms.

A traditional approach might wait for everything before sending the complete
page. Streaming allows the server to send the header and product information
first, followed by recommendations when they become available.

Out-of-order streaming goes further: independent portions of the page can be
delivered as soon as they're ready, even when that means they arrive in a
different order from the original component tree. The browser can place the
content in its correct location.

Why it matters:

- Faster initial display.
- Better perceived loading performance.
- Independent sections can load without blocking each other.

### Server Functions

Server Functions are functions that execute on the server but can be invoked
from client-side application code. For example, a user submits a registration
form. The client calls:

```
await registerUser({
  email: "user@example.com",
  password: "password"
});
```

The function executes on the server, where it can:

1. Validate the request.
2. Access the database.
3. Create the user account.
4. Return a result to the browser.

The browser does not need direct access to the database.

In React terminology, Server Functions are asynchronous functions marked with
`"use server"`.

They are useful for:

- Form submissions.
- Database updates.
- Authentication workflows.
- Data mutations.
- Other server-side operations.

Security consideration: Server Functions are network entry points. They must
validate input and enforce authorization. They should never assume that calling
them from an authenticated UI makes the request trustworthy.

## 5. Advanced UI interaction patterns

### Granular Optimistic UI

Optimistic UI means updating the user interface immediately, assuming that a
server operation will succeed, rather than waiting for confirmation. Granular
Optimistic UI applies this technique to individual pieces of UI rather than
updating an entire page or component.

Example: A user likes a social media post.

Traditional approach:

1. User clicks Like.
2. Browser sends request to server.
3. Server updates the database.
4. Server responds.
5. Browser updates the Like button.

Optimistic approach:

1. User clicks Like.
2. Browser immediately changes the button to Liked.
3. Browser sends request to server.
4. If successful, nothing further is needed.
5. If unsuccessful, the UI reverts to its previous state.

Granular means the individual Like button can update without waiting for or
re-rendering unrelated content. The application feels faster and more
responsive, even when network latency is significant.

### Single-Flight mutations

A mutation is an operation that changes data on the server.

Examples:

- Adding a product to a shopping cart.
- Updating a user's profile.
- Submitting an order.
- Liking a post.

Single-Flight mutations ensure that multiple equivalent requests are not
unnecessarily executed concurrently. Imagine a user rapidly clicks the Submit
button three times.

Without protection:

```
Click 1 → Request 1 → Create order
Click 2 → Request 2 → Create order
Click 3 → Request 3 → Create order
```

This could accidentally create three orders. With Single-Flight behavior only
one equivalent operation is in flight. Depending on the implementation,
subsequent callers may share the original promise or wait for its result.

Why it matters:

- Prevents duplicate operations.
- Reduces unnecessary network requests.
- Improves consistency.
- Helps avoid race conditions.

Single-Flight is not a substitute for server-side idempotency. For critical
operations such as payments and orders, the server should also use idempotency
keys or equivalent protections.

## 6. Putting the concepts together: Framework comparison

The following comparison illustrates how these concepts relate to different
frontend frameworks.

| Feature              | React                | SolidJS           | Svelte 5          |
| -------------------- | -------------------- | ----------------- | ----------------- |
| Primary reactivity   | Component state      | Signals           | Runes             |
| Virtual DOM          | Yes                  | No                | No                |
| Fine-grained updates | Through optimization | Yes               | Yes               |
| Manual memoization   | Commonly used        | Less common       | Often unnecessary |
| Streaming            | Yes                  | With integrations | With integrations |

Some important distinctions:

- React provides a flexible component-based model, with a large ecosystem and
  sophisticated server-rendering capabilities.
- SolidJS emphasizes fine-grained reactivity, avoiding the traditional Virtual
  DOM.
- Svelte 5 uses compiler-based transformations and reactive runes to minimize
  runtime overhead.

## 7. Summary: The concepts grouped by purpose

This is a useful way to organize the terminology when studying frontend architecture.

| Area                       | Concepts                                     |
| -------------------------- | -------------------------------------------- |
| Reactivity                 | Signals, unit of reactivity                  |
| Rendering performance      | Re-render problems, Virtual DOM, memoization |
| React programming          | useEffect, useMemo, useCallback              |
| Server/client architecture | Isomorphic frameworks, hydration             |
| Page architecture          | Islands                                      |
| Performance measurement    | Lighthouse                                   |
| Asynchronous rendering     | Suspense waterfalls, Out-of-Order streaming  |
| Server-side operations     | Server Functions                             |
| User experience            | Granular Optimistic UI                       |
| Request management         | Single-Flight mutations                      |

There are three major architectural questions behind most of these concepts:

1. How efficiently does a framework update the UI? This is where signals,
   Virtual DOM, re-rendering, and memoization come in.
2. How efficiently does a framework deliver the initial page? This is where
   server rendering, hydration, islands, streaming, and Suspense come in.
3. How efficiently does a framework handle user interactions? This is where
   Server Functions, Optimistic UI, and Single-Flight mutations come in.

Understanding these three dimensions makes it much easier to evaluate modern
frontend frameworks rather than simply comparing their feature lists.
